# Changelog

All notable changes to Wiedisync, consolidated into release eras (newest first). Each era summarises a range of point releases; for the full per-version detail see `git log` and the in-app "What's New" (`src/modules/changelog/ChangelogPage.tsx`).

## v4.28 — 2026-06-10

- **v4.28.0 — Confirmed home games auto-push to VolleyManager**: confirming a HOME game in Terminplanung (`confirm-home` or `manual-booking`) now fire-and-forget pushes its date/time/hall straight into VolleyManager via the writable indoor game API (`scripts/vm-push-game.mjs`), so the official SVRZ schedule mirrors our confirmed games without the spielplaner re-editing each game by hand in VM. The worker matches the exact VM fixture by OUR team's `staticTeamIdentifier` (`teams.team_id` minus `vb_`) against `svrz_games.raw.encounter.teamHome.staticTeamIdentifier` — drift-proof and team-precise, so a D1/D2 pair sharing an opponent name never cross-pushes: 1 open match → auto-push, 0 → `no_fixture`, 2+ → `needs_pick` (flagged for a manual fixture choice). It only ever sets date/time/hall with status preserved as `open`; it **never finalizes** (no `validateGames`/`waitingForApproval`). Migration **104** adds `halls.vm_hall_id` (KWI A/B/C + Döltschi 1/2 → the single VM Döltschi venue, backfilled) and `game_scheduling_bookings.vm_{game_id,pushed_at,push_status,push_error}` (both `fields:['*']` → no permission change). Confirmed home games in the dashboard show a VolleyManager status badge (in VM / sending / failed / no fixture / choose fixture) with a manual **Push to VM** retry and a fixture picker for the ambiguous case (`POST /admin/terminplanung/vm-push`, `VmPushStatus` in `HomeProposalReview`). `gameScheduling` i18n ×5. There is no dev VolleyManager — all pushes hit the live Swiss Volley system; direct edit works only while the fixture is `open` (pre-publication), after which VM requires the postponement workflow. Shipped to dev + prod (migration 104 + ext deploy + worker rsync + frontend, all both envs).

- **v4.28.0 — Scheduling mailbox (embedded IMAP)**: opponent email replies to scheduling invites now sync into the Terminplanung dashboard from the club's `volleyball@spielplanung.kscw.ch` Migadu mailbox (IMAP pull every 10 min, gated on `SCHEDULING_IMAP_PASSWORD`; replies sent over the existing SES SMTP as raw MIME so threading + Message-ID are preserved), matched to opponents by address — so scheduling correspondence lives in-app instead of a separate inbox. New `scheduling_emails` table (migration **100**), `scheduling-mailbox.js` endpoints, `useMailbox` hook + dashboard UI, and a `mailbox_sync` cron in kscw-hooks. Live dev + prod (verified syncing).
- **v4.28.0 — Deep security + logic audit remediation**: a full frontend + backend audit shipped in the same release. User-visible: broadcasts now correctly reach the "waitlisted" / "not-yet-replied" audiences (the filter matched nobody before — wrong status enum); scorer game dates no longer render "Invalid Date" on iOS (bare `YYYY-MM-DD` anchored); "Coach present" now resolves on the trainings/games/calendar pages (missing M2M `.members_id` expansion — the junction-ID ghost-member class); dates forced to Swiss `de-CH`. Backend/security: confirmed AWAY games now block scheduling correctly (a `timestamptz`→`::text` read bug silently disabled gap/same-day/cross-team checks); all five `getCurrentSeason()` copies aligned to the June cutover (writer/reader season-string mismatch was orphaning new `member_teams` rows June–Aug); per-team spielplaner scoping enforced (`spielplaner_assignments` — `is_spielplaner` stays club-wide by design); confirm-side guards added (derby clamp + booking-status); `sanitize-html.js` allowlist hardened (mXSS bypasses); public `events` read row-scoped to club-wide types; invite token dropped from the reissue response. Migrations **101–103** (search_path on 3 trigger fns / guest-block numeric guard / derby host-delete guard). Both CF Workers (`kscw-push`, `kscw-sentry-tunnel`) deployed with their hardening. Shipped dev + prod (release `e640bea9` + follow-up perms / ext / worker deploys). Report: `.planning/audits/2026-06-10-deep-audit.md`.

## v4.26 — 2026-06-08

- **v4.26.0 — Home-proposal invalidation + semi-automatic re-request (game scheduling)**: a pending home-slot proposal can silently rot after an opponent submits it — the slot gets booked by another game, blocked, hit by a hall closure, lands too close to a confirmed game, or falls before a confirmed derby. The admin dashboard now re-validates every pending home proposal live via `GET /admin/terminplanung/proposal-health` (mirrors the `confirm-home` guards that bite day-to-day: taken / team event / team block / hall closure / too close / derby / Döltschi cap + date; the rarer Saturday-cap and cross-team races stay enforced hard at confirm time, so a stale "valid" can never become a bad booking). Dead proposals are struck through with a reason and their confirm button disabled; when **all three** of an opponent's picks are gone, a banner offers a confirm-gated **"Email opponent for 3 new slots"** button → `POST /admin/terminplanung/request-new-slots` (race-guarded: refuses with `proposals_still_valid` unless genuinely all-dead) deletes the dead proposal, resets the opponent so their existing link works again, stamps `new_slots_requested_at`, and emails them (their language, with a CTA to their link) to pick three new slots; `propose-home` clears the flag on fresh proposals and the dashboard shows "Awaiting new proposals (asked dd.mm.yyyy)". Migration **091** adds `game_scheduling_opponents.new_slots_requested_at` (readable via the existing `fields:['*']` grant — no permission change). New `home_reproposal_request` email kind ×5 (the HTML layout now supports a CTA button) + `gameScheduling` i18n ×5. Shipped to dev + prod (migration 091 + ext deploy on both).
- **Döltschi = one slot per date (clarification)**: a Döltschi date counts as a single bookable game regardless of the time (19:00 / 20:30) or which hall (Döltschi 1 or 2) — so at most one Döltschi game per date, club-wide (was previously one per date+time). Applied to the slot-offer dedupe, the `confirm-home` guard, the new proposal-health check, and the slot-config preview.
- **Season overview calendar**: game-Saturdays (Spielsamstage) now render in gold with a "Spielsamstag" label beside the day number (the previous dark-amber read as brown in dark mode), and hall closures (Google-calendar + school holidays) render with a red day background. `CalendarGrid` gained opt-in `highlightClassName` + `highlightLabel` props (other calendars unchanged) and a dark-mode-visible closure overlay.

## v4.25 — 2026-06-08

- **Döltschi scheduling rules (backend-only)**: junior (Under) teams now always get the shared VB Döltschi pool (Döltschi 1 + 2) even when it isn't their own slot, plus the Spielhalle pool (both), on top of their Sunday slots — `generate-slots` now tags each standard slot's source individually so the Friday VB/BB alternation still applies only to Spielhalle. Döltschi is capped at **10 games per season club-wide** and never **two simultaneous games** (Döltschi 1 + 2 = one venue for games → one game per date+time): enforced at slot-offer time (`slots/:token` drops Döltschi slots over the cap or whose date+time is already booked, and dedupes 1+2 to one offer per time) and again in the `confirm-home` booking transaction. Backend-only (slot generation + opponent offer flow); not member-app-visible → no app-version bump. Shipped to dev + prod (ext deploy both).
- **v4.25.0 — Intra-club derby anchoring (Art. 27 SVRZ)**: when two KSCW teams share a league group (e.g. H1 & H3 in 2L), SVRZ Art. 27 Abs. 6 requires their two head-to-head games to be the first game of the Vor- and Rückrunde (home team forfeits otherwise — and the Spielplanraster's order is overridden). New `game_scheduling_derbies` table (migration 090) + admin **DerbyPanel** in the scheduling setup: detects pairs from the all-KSCW fixtures in the synced SVRZ feed, surfaces the round the feed currently files them under (e.g. "Runde 7"), and lets the spielplaner fix the two dates (one Vorrunde leg, one Rückrunde leg; confirming requires one per half). Once confirmed, `game-scheduling.js` clamps the opponent flow for BOTH teams — home-slot offers, the away-date calendar, and the away-proposal server check — to dates after the relevant derby date per half, and feeds the derby dates into the game-spacing gap. Vor-/Rückrunde boundary derived as 01.01 of the season's second year (no config). The derby table is endpoint-gated (knex, admin/spielplaner) — no item permissions; inert until a derby is confirmed. New `gameScheduling` i18n ×5 + `away_before_derby` opponent message. Deployed to dev + prod (migration 090 + ext deploy on both).

## v4.24 — 2026-06-08

- **v4.24.1 — Coaches section on the team page + team-chat hidden for non-participants**: non-playing coaches are pulled out of the player roster into a dedicated **Coaches** table on `TeamDetail` (mirrors the Guests table). Split rule: a member in `team.coach` with no real playing position (only `other`/empty) is treated as non-playing staff and excluded from `rosterMembers`/`guestMembers`; a **player-coach** (coach who also has a playing position) stays in the roster with their coach badge. The section also fetches coaches attached only via `teams_coaches` (no `member_teams` row) so it's complete on any team. The **team-chat section now hides entirely for non-participants**: `TeamMessagesSection` owns the `useConversations` lookup and returns `null` when team chat is enabled but, after the conversation list loads, the caller has no conversation for this team (e.g. an admin/coach viewing a team they're not on) — previously this sat on "Loading messages…" forever. Members who turned team chat off still see the section so the "enable team chat" banner can prompt them. `TeamMessagesTab` refactored to receive `conv`/`isLoading`/handlers as props (no duplicate subscription). New i18n: `teams.coaches` + `messaging.notTeamMember` ×5 locales. Frontend-only; no migration/perms.
